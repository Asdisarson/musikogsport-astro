## Critical  (affect the currently-live BACS checkout — not a future-only concern)

> All three are one failure family: **a transport error / timeout on the money path throws uncaught instead of degrading gracefully, and leaves zero server-side trace.** Fixing #1 (the shared client) covers most of #2/#3's surface. These hit the **live BACS checkout today** — a transient upstream hiccup mid-checkout throws a raw 500 at a real customer; they are not gated on the Straumur card launch (only #4 is). They are hardening/observability gaps under failure conditions, not active exploits or guaranteed-broken flows.

1. **OBS · `src/lib/storeApi.ts:26` (+ timeout `:33`)** — `storeFetch`'s `try/catch` wraps **only** the `JSON.parse` (lines 40-44); the `await fetch(...)` and its `AbortSignal.timeout(25000)` are **outside** it. A network failure or 25s abort *throws* instead of returning `{ ok:false }`, so `respondCart`'s `console.warn` never fires **and** every caller below gets an uncaught exception. This is the root cause of #2 and the cart-route warnings.
2. **OBS · `src/pages/api/checkout.ts:26`** — order placement is a bare `await checkout(body, token)` with no `try/catch`. A Store API timeout/network failure during checkout throws → Astro returns a raw **500** to the customer (no localized error) with **no `[store-api]` breadcrumb**. The money path is exactly the case that's blind.
3. **OBS · `src/pages/utskra/takk.astro:25` + `src/lib/woo.ts:147`** — post-payment confirmation double-swallows: `getOrder(...).catch(() => null)` on the page, and `getOrder` itself catches the `wooGet` throw silently. When the order lookup fails *right after a successful payment*, the customer sees "Pöntun fannst ekki" and there is no trace distinguishing a real not-found from a Woo outage — the highest-stakes path.

## Warning  (fix this sprint)

### Security / correctness
4. **SEC · `src/components/CheckoutForm.tsx:179`** — post-payment redirect validates **scheme only** (`https:` OR same-origin), no host allowlist: `redirect_url` from the upstream response goes straight to `window.location.href`, so a tampered backend response could redirect to any `https://…`. Carries the team's own `TODO(go-live): tighten … to a Straumur host allowlist`. Tighten to scheme **+** Straumur-host allowlist.
5. **TYPE · `src/lib/decode.ts:24`** — `String.fromCodePoint(num)` throws `RangeError` for `num > 0x10FFFF`; the guard checks `Number.isFinite` but **not range**. Reachable via a malformed numeric entity (`&#9999999;`) in a product name → uncaught **SSR 500** (runs in `.astro` frontmatter). One-line fix: `num >= 0 && num <= 0x10FFFF`.
6. **SEC · `src/pages/api/checkout.ts:14-26`** `[?]` — only `billing_address.email` + `payment_method` are validated; the rest of `CheckoutPayload` (`shipping_address`, `payment_data[]`, `customer_note`, all other billing fields) is cast and forwarded raw. Defensible if "Store API is the trust boundary" is the intent, but it's the one mutation route that bypasses field-level guards.
7. **TYPE · `src/components/CheckoutForm.tsx:128,138-139,155`** `[?]` — Postis locker fields (`postis_dpo_postbox`/`postis_dpo_phonenumber`) are spread at the **top level** of the checkout body but aren't modeled in `CheckoutPayload` and aren't validated. Runtime delivers them, but whether the Postis plugin reads top-level vs nested params is unverified — if it strips them, the chosen locker is silently dropped at order placement. Confirm against the plugin.

### API / interface consistency
8. **API · `src/pages/api/products.ts:29`** — returns `{ error:'catalog_unavailable' }` on 502: wrong key (`error` vs house `message`) and a machine code the storefront's errors don't use.
9. **API · `src/pages/api/waitlist.ts:21-25`** — upstream `fetch` has **no `try/catch` and no `AbortSignal.timeout`**, unlike its proxy siblings (`droppoints` 10s+502, `products` 502). WP unreachable → unhandled **500** (family standard is 502) and it can hang on the platform default. Also no `[prefix]` log.
10. **API · `src/pages/api/posturinn/droppoints.ts:26-30`** — the passthrough branch applies `Cache-Control: public, max-age=600` using the upstream status **verbatim**, so an upstream **4xx/5xx error body gets cached publicly for 10 min**. Gate the 600s cache to 200s; fall back to `no-store` on error.
11. **API · `src/pages/api/waitlist.ts:13` vs `droppoints.ts:18`** — same plugin-proxy family, same condition (bad input → 400), divergent shapes: `{ message }` vs `{ ok:false, code, items }`. Pick one.
12. **API · `src/pages/utskra/takk.astro`** `[?]` — `prerender=false` page that fetches/renders order PII but sets **no `Cache-Control`**, while every PII *API* route uses `no-store`. An intermediary could cache the receipt HTML.

### Cross-lens notes — fix at the boundary, not the call sites
- **One root fix collapses the Critical trio + #13/#14/#15/#16.** Both upstream clients have the same defect: the `await fetch` sits **outside** the `try`. Harden **two functions**:
  - `storeFetch` (`storeApi.ts:26`) — wrap `await fetch` in the try, return `{ ok:false }` on throw, log abort-vs-error distinctly.
  - `wooGet` (`woo.ts`) — same; it *additionally* throws on `!res.ok`, and every `.catch(() => [])` SSR site in #15/#16 swallows that throw silently.
  Logging once at these two boundaries closes the money-path blindness **and** the systemic catalog blindness — that's ~2 edits, not the ~12 you'd get by patching each route/page. **Caveat:** `index.astro` fires ~5 parallel `wooGet`s, so log at the boundary with a level/dedup that won't spam SSR logs under a full outage.
- **⚠️ Verify-first real bug — #7 (Postis fields).** Marked `[?]`, but if the Postis plugin reads nested (not top-level) params, the customer's chosen parcel locker is **silently dropped at order placement** — a fulfillment bug, not a style nit. Confirm against the plugin's param source *before* the cosmetic Warnings.
- **Type-safety is genuinely clean** — zero `as any`/`@ts-ignore`, all external-nullable derefs guarded, price math correct for zero-decimal ISK, no floating promises, no hydration hazards. Only #5 and #7 surfaced.
- **Security is solid** — anti-enumeration (constant-time key compare), env split (no secret reaches the client bundle), all `set:html` sanitized, cookies httpOnly. The only real gaps are the redirect allowlist (#4) and the absent rate limit (Info).
